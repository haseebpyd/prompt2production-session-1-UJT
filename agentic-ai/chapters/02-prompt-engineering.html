M2: Prompt Engineering for Engineers

Prompts are production interfaces. In this module you stop improvising chat messages and start shipping versioned, tested, parameterized prompt artifacts — with a clear framework, failure-mode toolkit, and basic evaluation habits you will deepen later in M12.

Learning objectives

  • Write reliable prompts with a structured, repeatable framework
  • Apply zero-shot, few-shot, role, and chain-of-thought where each actually helps
  • Design system prompts and message structures fit for production apps
  • Diagnose hallucination, format drift, refusals, and basic prompt injection
  • Treat prompts as versioned, tested engineering artifacts — not throwaway text

2.1 Anatomy of a Prompt (Message APIs)

Chat models expect a list of messages with roles. Exact role names differ slightly by provider, but the engineering idea is stable:

Role Purpose Notes
system Persistent policy: identity, tools allowed, output rules, safety Keep stable; version it
developer Provider-specific “higher priority” instructions (e.g. some OpenAI models) Check current provider docs
user Task + untrusted input (customer text, documents, UI fields) Never trust as instructions
assistant Prior model turns (history) or few-shot demonstrations Manage length vs quality
tool / function Results of tool calls (M3) Return structured facts, not essays 
messages = [
    {"role": "system", "content": SYSTEM_PROMPT_V3},
    {"role": "user", "content": f"Customer email:\\n```\\n{email_text}\\n```\\nClassify urgency."},
]

Delimit untrusted content. User text that says “ignore previous instructions” should be data inside fences — not peer instructions.

2.2 Six-Part Prompt Framework

Use the same skeleton every time. Empty sections are fine; missing structure is what produces flaky outputs.

1. ROLE

Who the model is acting as (senior backend eng, compliance reviewer, …).

2. TASK

Single clear verb + outcome (“Extract X”, “Decide Y”, “Rewrite Z”).

3. CONTEXT

Facts the model needs: product rules, schemas, excerpts, prior decisions.

4. CONSTRAINTS

What not to do: no speculation, no extra keys, cite only provided text, length limits.

5. FORMAT

Exact shape: JSON schema, Markdown sections, bullet count, field names.

6. EXAMPLES

Few-shot I/O pairs that demonstrate edge cases (empty input, ambiguity, refusal).

Weak vs rebuilt

Weak

Summarize this and make it nice.

Rebuilt (sketch)

Role: Technical editor for SaaS release notes.
Task: Summarize the release notes for engineers.
Context: {{notes}}
Constraints: No marketing adjectives; max 5 bullets;
  only facts present in the notes.
Format: Markdown bullets only.
Examples: (1) empty notes → "No changes."
          (2) mixed features/fixes → separate sections.

2.3 Core Techniques

Zero-shot

Task description only. Prefer for simple, well-specified jobs when models are strong and format is trivial.

Few-shot

Show 2–5 input→output examples. Best for format lock, label inventories, and rare edge cases. Bad examples poison the model — curate them.

Role / persona

Useful when domain judgment matters. Useless cosplay (“you are a pirate”) wastes tokens — be specific about standards and audience.

Delimiters & output priming

Fence documents with ``` or XML tags. Optionally end the assistant turn priming with { or a header so completion continues in-format.

# Few-shot label lock example (conceptual)
SYSTEM = """You classify support tickets.
Labels: billing | bug | feature | other
Reply with ONLY the label."""

shots = [
    ("I was charged twice.", "billing"),
    ("App crashes on login.", "bug"),
]
# Build user/assistant pairs, then the real ticket as the final user message.

2.4 Reasoning Techniques

Chain-of-thought (CoT) asks the model to work step-by-step before the final answer. Classic “think step by step” still helps weaker models on multi-hop problems — but it also leaks reasoning into logs and increases tokens.

  • Self-consistency — sample multiple CoT paths at higher temperature; majority-vote the final answer for hard classification / numeric tasks.
  • Reasoning models — when available, prefer them for hard multi-step work and reduce handcrafted CoT scaffolding. Measure cost/latency.
  • When not to CoT — strict JSON extraction, simple classification, anything where extra tokens cause format drift.
Separate scratchpad from customer-facing answer. If you need intermediate reasoning, put it in a dedicated field you discard, or use provider “thinking” channels — do not dump chain-of-thought into UI by default.

2.5 Controlling Output & Failure Modes

Failure Symptom First fixes
Hallucination Invented facts, fake citations, phantom APIs Ground on provided context; “say unknown”; retrieval (Part II); lower temp
Format drift Markdown instead of JSON; extra keys; prose preambles Few-shot + schema; structured outputs (M3); reject/retry
Refusals / over-refusal Model declines valid business tasks Clarify allowed scope; provide policy; reduce ambiguous “do anything” personas
Prompt injection User/doc text overrides system policy Delimit; dual-channel design; treat retrieved text as untrusted; later: M13 guardrails

Defensive system-prompt patterns

  • State that user/document content is data, not instructions.
  • Require refusals when asked to ignore policies.
  • Pin the output contract (“valid JSON only; no markdown fences”).
  • Prefer tool use for side effects — never “just trust” the model to have done something.

2.6 Prompt Management: Templates, Versioning, Caching

Production prompts live in git. Prefer templates (Jinja2 or similar) with explicit variables — never string-concatenate customer input into the middle of instructions without delimiters. 

# prompts/summarize_v2.j2
{# version: summarize@2.1.0 #}
You are a technical summarizer for {{product_name}}.
Task: Produce exactly {{n_bullets}} bullets.
Constraints:
- Use only facts in the source.
- If source is empty, reply: NO_CONTENT
Source:
```
{{ source }}
```
  • Version — summarize@2.1.0 in filename or frontmatter; log version with every request.
  • Parameterize — product name, bullet count, locale, tone — test combinations.
  • Prompt caching — some providers discount stable system/prefix tokens. Keep long stable prefixes first; put volatile user content at the end. See provider docs for Anthropic/OpenAI caching.

2.7 Prompt Evaluation Basics

You do not need a full eval platform yet (that is M12). You do need a golden set: 10–50 fixed inputs with expected properties (exact label, JSON keys present, must-include phrases, must-not-include phrases).

  • Run prompt A vs B offline; score pass rate on the golden set.
  • Never tune prompts against the same tiny ad-hoc example you are staring at — expand the set.
  • Track regressions when you bump models.

Later you will use promptfoo / LangSmith / RAGAS. For now: pytest + JSON fixtures is enough.

Hands-on Labs

Lab A — Rebuild a weak prompt

Take a one-line prompt. Rewrite with the six-part framework. Score both on 10 fixed inputs with a simple rubric (0–2). Report before/after.

Lab B — Few-shot format lock

Force a strict line-oriented or JSON-ish format using examples only (no schema API yet). Measure consistency over 20 runs.

Lab C — CoT vs reasoning model

Same multi-step word problems on (1) instruct model + CoT and (2) a reasoning model if available. Compare accuracy, latency, and token cost.

Lab D — Prompt-injection red team

Craft a user message that tries to override the system prompt (e.g., exfiltrate secrets or change output format). Harden the system prompt and re-test. Document attacks that still work.

Lab E — Template library

Create a small Jinja (or equivalent) library with version metadata and a loader that rejects unknown versions.

Mini Project — Prompt-Powered Text Toolkit

Ship a small app (CLI or FastAPI) exposing four reliable prompt tools, each backed by a versioned template and a golden test set.

1. Summarize — N bullets, grounded, empty-safe
2. Extract entities — fixed schema (name, email, company, dates…)
3. Classify sentiment — closed label set only
4. Rewrite tone — professional / concise / friendly modes

Acceptance criteria

  • ☐ Four tools callable via consistent API (e.g. POST /tools/{name} or CLI subcommands)
  • ☐ Each prompt template versioned and loaded from disk (not hard-coded in call sites)
  • ☐ Golden set ≥ 8 cases per tool; automated tests fail the build if pass rate < threshold (document threshold)
  • ☐ README explains how to run tests without burning unlimited API quota (optional --dry-run / recorded fixtures welcome)
  • ☐ One page: before/after quality story for the weakest tool

You will tighten JSON contracts in M3 — for now focus on prompt quality and evaluation discipline.
