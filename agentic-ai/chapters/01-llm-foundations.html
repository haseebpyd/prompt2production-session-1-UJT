1.2 How Models Are Made (Engineer’s View)

You will almost never train from scratch. You will choose among model types shaped by this lifecycle:

  1. Pretraining — predict the next token on enormous corpora. Produces a base model that continues text but does not reliably follow instructions.
  2. Supervised fine-tuning (SFT) — train on curated instruction–response pairs. Produces an instruct / chat model.
  3. Preference optimization (RLHF / RLAIF) — align outputs with human or AI preference signals. Improves helpfulness and reduces some failure modes.
  4. Reasoning / test-time compute models — models trained or prompted to spend more tokens “thinking” before answering (o-series style, extended thinking). Often replace manual chain-of-thought prompting for hard problems.

Base

Completion engines. Useful for research / fine-tuning; awkward for apps.

Instruct / chat

Default for APIs. Message roles, system prompts, tool calling.

Reasoning

Better on multi-step tasks; higher latency and cost per answer.

1.3 Transformer Intuition (No Heavy Math)

An LLM is a neural network that maps a sequence of tokens to a probability distribution over the next token. Generation is a loop: sample (or greedily pick) one token, append it, repeat until a stop condition.

Embeddings

Tokens become vectors. Nearby vectors mean related usage in the training distribution — not “true meaning,” but useful geometry.

Self-attention

Each position looks at others in the context window to decide what matters for the next prediction. That is why long-range context works (until you hit the window or the middle gets “lost”).

Next-token prediction

Everything — code, JSON, “reasoning” — is still token sampling. Structure and truth are not guaranteed; your prompts, tools, and evals make them reliable enough for products.

Engineer’s takeaway: LLMs are stochastic pattern completers with enormous capacity. Treat outputs as hypotheses to validate — never as ground truth — especially for citations, APIs, and security-sensitive decisions.

1.4 Tokenization, Context Windows & Cost

Models do not “see” characters or words. A tokenizer (commonly BPE — Byte Pair Encoding) splits text into tokens. English averages roughly 4 characters per token; code and non-English often use more tokens for the same human-readable length.

  • Prompt / input tokens — everything you send (system + history + user + tools).
  • Completion / output tokens — everything the model generates (usually billed higher per token).
  • Context window — max tokens of history the model can attend to in one call. Excess is truncated or rejected.

Rough cost mental model:

estimated_usd ≈ (input_tokens / 1e6) * input_price_per_1M
              + (output_tokens / 1e6) * output_price_per_1M

Always count tokens before shipping a hot path. A 50-page PDF stuffed into the prompt can cost more than a retrieval pipeline that pulls three relevant chunks.

Tokenizer lab (tiktoken)

import tiktoken

enc = tiktoken.encoding_for_model("gpt-4o")  # or get_encoding("o200k_base")
prompt = "Summarize this API design in 5 bullets."
tokens = enc.encode(prompt)
print(len(tokens), tokens[:20])

# Pseudo-price example — replace with current provider rates
INPUT_PER_1M = 2.50
print(f"≈ ${len(tokens) / 1e6 * INPUT_PER_1M:.6f} input")

Docs: openai/tiktoken. Note: Anthropic and Google use different tokenizers — count with their tooling when estimating those bills.

1.5 Inference / Decoding Parameters

These knobs do not “make the model smarter.” They change the sampling distribution over next tokens.

Parameter What it does When to use
temperature Scales logits before sampling. Low → peaked; high → flat / creative. 0–0.3 extraction/code; 0.7–1.0 brainstorming
top_p Nucleus sampling: only sample from the smallest set of tokens whose cumulative probability ≥ p. Often leave default; avoid stacking wild temp + wild top_p
top_k Restrict to k most likely tokens (provider-dependent). Less common on OpenAI-style APIs
max_tokens Hard cap on completion length. Always set for cost control
stop Stop sequences that end generation early. Enforcing delimiters / ending a format
seed Best-effort reproducibility (not guaranteed across providers/versions). Eval suites, demos
frequency / presence penalty Discourage repetition (OpenAI-style). Long creative text; rarely for JSON

Determinism myth: Even temperature 0 can vary across GPUs, batching, or model version upgrades. For production evals, freeze model IDs, versions, and seeds — and still expect occasional drift.

1.6 Model Landscape (2025–2026)

Know families, not brand slogans. Prices and names change; selection criteria stay:

  • Capability — reasoning, coding, long context, multimodal, tool use quality
  • Latency — TTFT and tokens/sec for your UX
  • Cost — input vs output pricing; caching; batch APIs
  • Operational fit — data residency, rate limits, structured outputs / tools support

Frontier hosted

  • Anthropic Claude — Opus / Sonnet / Haiku tiers · docs
  • OpenAI GPT & o-series · docs
  • Google Gemini · docs

Open-weight / local-friendly

  • Llama, Qwen, Mistral, DeepSeek families
  • Run via Ollama, LM Studio, or vLLM
  • Great for offline, privacy, and cost at scale — quality varies by size

Multimodal models accept images (and sometimes audio/video). Reasoning models trade speed/cost for harder problem performance. Default course posture: prototype on a mid-tier frontier model; measure; then decide to upgrade, downgrade, or go local.

1.7 Hosted APIs vs Local Inference

Hosted APIs

  • Fastest path to quality; operational burden on vendor
  • Pay per token; watch rate limits (RPM / TPM)
  • Data leaves your laptop — review vendor retention policies

Local / self-hosted

  • Privacy and predictable unit cost after GPUs
  • You own serving, quantization, and scaling (vLLM)
  • Quality and tool/JSON reliability may lag frontier APIs

Production systems often mix: frontier for hard reasoning / customer-facing quality; local or small models for classification, routing, or high-volume cheap tasks.

1.8 Professional Environment Setup

Minimum bar for this course:

  • Python 3.11+
  • Dependency isolation with uv (preferred) or venv
  • Secrets in .env — never committed; load with python-dotenv
  • Official SDKs: openai, anthropic, google-genai (or google-generativeai)
  • Basic cost logging: model, tokens in/out, latency ms, estimated USD
# .env (example — do not commit)
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
GOOGLE_API_KEY=...

# uv quickstart
# uv init aai-lab && cd aai-lab
# uv add openai anthropic google-genai python-dotenv tiktoken httpx
import os, time
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()  # reads OPENAI_API_KEY

t0 = time.perf_counter()
resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Reply with exactly: pong"}],
    max_tokens=16,
    temperature=0,
)
latency_ms = (time.perf_counter() - t0) * 1000
usage = resp.usage
print(resp.choices[0].message.content)
print(f"{latency_ms:.0f}ms | in={usage.prompt_tokens} out={usage.completion_tokens}")

Mini Project — Model Benchmark CLI

Build a Python CLI that runs a fixed task suite across several models and emits a comparison report. You will reuse this repo for the rest of the course whenever you need to pick a model.

Required tasks (minimum)

  • Summarization — summarize a ~400-word article into 5 bullets
  • Classification — label sentiment as positive / negative / neutral (strict labels)
  • Code generation — implement a small pure function from a docstring; optionally run it

Report fields

  • Model ID, provider, latency (ms), prompt tokens, completion tokens, estimated cost
  • Raw output (or truncated) + qualitative notes (rubric: correctness, format adherence, usefulness)
  • Export Markdown and CSV

Acceptance criteria

  • ☐ CLI entrypoint documented in README (uv run … or equivalent)
  • ☐ At least 2 providers (3 preferred) and configurable model list via YAML/JSON
  • ☐ Fixed prompts checked into the repo (no hidden manual editing during a run)
  • ☐ Markdown + CSV artifacts written under reports/
  • ☐ Secrets only via env; sample .env.example committed
  • ☐ One-page write-up: which model you would pick for each task and why

Suggested layout: tasks/, providers/, reports/, bench.py.
