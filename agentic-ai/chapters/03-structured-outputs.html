M3: Structured Outputs, Function & Tool Calling

Free-text answers are fine for chat. They break pipelines. This module teaches you to treat the model as a typed component: schema-constrained outputs, validation/retry, and the tool-call loop that later powers agents — implemented by hand before you reach for agent frameworks.

Learning objectives

  • Force valid, schema-constrained data reliably enough for real pipelines
  • Implement function/tool calling to connect models to your code and external APIs
  • Validate, parse, and repair model output defensively
  • Understand the tool-call mechanics that later power agents (Part III)

3.1 Why Free Text Breaks Pipelines

Downstream code expects contracts: field names, types, enums, nullability. Models prefer prose. Even a “please return JSON” prompt fails under load — preambles (“Sure!”), trailing commas, wrong types ("42" vs 42), missing keys, invented keys.

Chat product

Human reads ambiguity. OK for demos.

Automation

One bad parse = failed job, wrong DB write, or silent corruption.

Engineering fix

Schema + validation + retry + typed errors. Never “best effort JSON.”

3.2 JSON Mode, JSON Schema & Native Structured Outputs

Providers give escalating guarantees:

  1. Prompt-only JSON — weakest; always validate.
  2. JSON mode / response_format json_object — encourages valid JSON object, not your schema.
  3. Structured outputs / JSON Schema — constrains to a schema (provider-dependent maturity).
# OpenAI-style sketch — check current docs for exact API
from openai import OpenAI
client = OpenAI()

schema = {
    "type": "object",
    "properties": {
        "sentiment": {"type": "string", "enum": ["positive", "negative", "neutral"]},
        "confidence": {"type": "number", "minimum": 0, "maximum": 1},
    },
    "required": ["sentiment", "confidence"],
    "additionalProperties": False,
}

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Review: shipping was late but support helped."}],
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "sentiment_result", "schema": schema, "strict": True},
    },
)

3.3 Pydantic as the Data Contract (+ Instructor)

In Python, Pydantic models are your product types. Libraries like Instructor wrap provider calls to return validated models and retry on validation failure. 

from pydantic import BaseModel, Field, EmailStr
from typing import Optional
import instructor
from openai import OpenAI

class InvoiceLine(BaseModel):
    description: str
    amount_usd: float = Field(ge=0)

class Invoice(BaseModel):
    vendor: str
    invoice_id: str
    total_usd: float = Field(ge=0)
    contact_email: Optional[EmailStr] = None
    lines: list[InvoiceLine]

client = instructor.from_openai(OpenAI())

invoice = client.chat.completions.create(
    model="gpt-4o-mini",
    response_model=Invoice,
    messages=[
        {"role": "system", "content": "Extract invoice fields. Invent nothing. Use null when missing."},
        {"role": "user", "content": raw_email_text},
    ],
    max_retries=2,
)
Validation failure is a feature. Retry with the error message fed back to the model, or fail the request with a typed 422 — do not silently coerce garbage into your database.

3.4 Function / Tool Calling Loop

Tools let the model choose when to call your functions. You still own execution, permissions, and side effects. The canonical loop (names vary by SDK):

User request
→
Model (± tool_calls)
→
Your code runs tool
→
tool_result message
→
Final answer
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get current weather for a city",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string"},
                "unit": {"type": "string", "enum": ["c", "f"]},
            },
            "required": ["city"],
        },
    },
}]

def get_weather(city: str, unit: str = "c") -> dict:
    # Replace with real API; never execute unreviewed code from the model
    return {"city": city, "temp": 22, "unit": unit}

# Pseudocode loop:
# 1) send messages + tools
# 2) if finish_reason/tool_calls: execute each call safely; append tool results
# 3) call model again until a normal assistant message (or max rounds)
  • tool_choice — auto | force a tool | none (provider names differ).
  • Parallel tool calls — models may request multiple tools in one turn; execute concurrently when safe; preserve call IDs in results.
  • Streaming — tool call arguments may arrive in chunks; buffer until complete before executing.
  • Security — allowlist tools; validate arguments with Pydantic; never eval; treat model as untrusted for authz.

3.5 Defensive Parsing, Repair & Fallbacks

Even with structured modes, build a belt-and-suspenders parser layer:

  1. Strip markdown fences if present.
  2. json.loads → Pydantic model_validate.
  3. On failure: optional repair prompt (“Return valid JSON conforming to this schema. Errors: …”).
  4. Cap retries (e.g. 2). Then return a typed error to the client.
  5. Fallback: smaller specialized model, regex for highly constrained fields, or human review queue.
import json, re
from pydantic import ValidationError

def extract_json_object(text: str) -> dict:
    text = text.strip()
    fence = re.search(r"```(?:json)?\\s*([\\s\\S]*?)```", text)
    if fence:
        text = fence.group(1).strip()
    return json.loads(text)

def parse_invoice(text: str) -> Invoice:
    try:
        return Invoice.model_validate(extract_json_object(text))
    except (json.JSONDecodeError, ValidationError) as e:
        raise ValueError(f"invalid_invoice_payload: {e}") from e

3.6 Cost & Latency of Constrained Generation

  • Structured outputs can add TTFT or token overhead depending on provider implementation.
  • Retries multiply cost — log failure rates; fix prompts/schemas before raising max_retries.
  • Tool loops add round-trips — set max_rounds, cache tool results, and avoid chatty tools.
  • Prefer extracting once into typed state, then template the user-facing prose — do not re-prompt for format if you already have fields.

Mini Project — Structured Data Extraction Service

A FastAPI endpoint that accepts raw documents and returns validated, typed JSON — with retry/repair, clean errors, and a test suite for malformed inputs.

Suggested API

POST /extract
Content-Type: application/json
{ "document_type": "invoice", "text": "..." }

# 200 → { "data": { ...typed... }, "meta": { "model", "retries", "latency_ms" } }
# 422 → { "error": "validation_failed", "details": [...] }

Acceptance criteria

  • ☐ FastAPI app with OpenAPI schema reflecting your Pydantic models
  • ☐ At least one document_type fully implemented (invoice or support email)
  • ☐ Validation + max 2 retries/repairs; meta includes retry count
  • ☐ Pytest suite: happy path, missing fields, garbage input, oversized input policy
  • ☐ README with run instructions, env vars, and sample curl
  • ☐ No secrets committed; rate-limit note in README

This service becomes a building block for later RAG/agents: extract → store → retrieve → answer with citations.
