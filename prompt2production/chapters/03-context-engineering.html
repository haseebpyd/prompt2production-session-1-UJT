3a. Context Engineering

Curate what the model sees — not just how you ask. Essential for agents, RAG, and Cursor workflows.

Source: Panaversity — Context Engineering Tutorial

What Is Context Engineering?

Context engineering is designing dynamic systems that give an LLM the right information, in the right format, at the right time.

André Karpathy analogy: The LLM is the CPU; the context window is the RAM. Context engineering optimizes how you use that limited memory.

Prompt vs Context Engineering

Aspect Prompt engineering Context engineering
GoalHow to behave & what to produceFacts the model should rely on
LeversRole, constraints, JSON schema, few-shotRAG, docs, @codebase, tools, memory
WhenChatGPT conversationsAI apps & agents (autonomous, multi-turn)
Failure modeWrong format / vague outputHallucinations / outdated answers

One-liner: Prompt engineering is how you ask; context engineering is what you show. Combine both for reliable apps.

Six Components of AI Agents

1. Model

Core engine (GPT, Claude, Gemini)

2. Tools

APIs, databases, calendar, email

3. Knowledge & Memory

Static docs + conversation history

4. Audio & Speech

Voice input/output

5. Guardrails

Safety, tone, compliance filters

6. Orchestration

Deploy, monitor, improve

Context engineering is the "assembly instructions" that tell all six parts how to work together.

Practical Checklist (Anthropic)

  • Write a minimal, sectioned system prompt — add guidance only when tests fail
  • Trim your toolset — each tool should be obvious and token-efficient
  • Keep 3–7 canonical examples; move edge cases to retrieval
  • Start small upfront, fetch details just-in-time via tools (not stuffing context)
  • For long tasks: compact history, maintain NOTES.md-style memory, use sub-agents

Example: AI Research Assistant Output Contract

A context-engineered prompt defines role, steps, and a strict JSON schema — the model cannot improvise format.

Role: AI research assistant focused on recent AI trends.

Task: Break <user_query> into subtasks; return JSON per schema; summarize in 300 words.

Output schema (each subtask):
{ "id", "query", "source_type", "priority", "start_date", "end_date" }

Constraints: Past 10 days only. JSON only. No fluff.
